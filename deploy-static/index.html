静态网页部署，从 0 到 1

把一个 index.html 变成全世界都能访问的网址，而且完全免费、大厂托管、稳定可靠。只讲两个值得信赖的平台：GitHub Pages 和 Cloudflare Pages。最后专门一章教你全程让 AI 一口气发布——账号、命令、授权，全给齐。

🆓 永久免费额度 🏢 微软 / Cloudflare 背书 🔒 自动 HTTPS 🤖 可全程 AI 操作
本教程覆盖的"全方位"是指：概念原理 → 平台选型 → 账号准备 → 两个平台各自从 0 到 1 的完整发布 → 自定义域名 → 静态能力边界（能做什么/不能做什么/怎么补） → 全程 AI 自动发布的完整命令清单 → 排错。跟着做，你手上这个 tutorials 站点就是活教材。
起点 · 先分清"静态"和"动态"

第 0 章：什么是"静态页部署"？

搞懂这个词，你才知道为什么它能免费、又有什么做不了

"部署"就是把你电脑里的网页文件，放到一台 24 小时开机的服务器上，让全世界通过一个网址访问。而"静态"是关键定语：

🔀 静态 vs 动态（一句话区分）
静态网站
服务器上放的就是写好的成品文件（HTML/CSS/JS/图片）。谁来访问，服务器都把同一份文件原样发出去，不在服务器上"现算"。你做的教程、博客、作品集、落地页，基本都是静态。
动态网站
每次访问，服务器要现场运行程序、查数据库再生成页面（如淘宝的"我的订单"、每人看到的内容不同）。需要后端、数据库，要花钱养服务器。

你现在这套教程合集（index.html + 几个子文件夹），就是纯静态——里面的动画是浏览器里跑的 JS，服务器只需老老实实把文件递出去。正因为服务器"不用干活、只发文件"，成本极低，大厂才愿意免费送。

验证方法 · 判断你的项目是不是静态
  1. 看你的项目文件：如果双击 index.html 就能在浏览器直接打开、功能正常，它就是静态的——因为它不依赖任何后端服务器。
  2. 反例自查：如果页面需要"登录后显示我的数据""提交表单存进数据库""调用你自己写的后端接口"，那部分就是动态，纯静态托管做不了（第 7 章讲怎么补）。
验证到了什么：能离线双击打开即用 = 静态 = 可免费托管。
原理 · 免费背后的逻辑

第 1 章：为什么大厂敢让你永久免费用？

理解这点，你就不会担心"免费的哪天跑路"

三个原因，让"静态托管免费"变得对大厂来说无所谓：

  • 成本极低：静态文件放在 CDN内容分发网络 上，全球缓存、按需分发，单个小站点几乎不消耗资源。
  • 战略引流：GitHub Pages 让你更离不开 GitHub 生态；Cloudflare 用免费 Pages 把你引进它的 CDN/安全体系，将来买它别的服务顺理成章。
  • 口碑与开发者黏性：免费额度是获取开发者信任的最好广告。
所以"免费"不是慈善，是双赢，因此长期稳定：GitHub Pages 由微软旗下 GitHub 运营、Cloudflare Pages 由纳斯达克上市公司 Cloudflare 运营。它们的免费静态托管跑了很多年、服务了海量项目。这正是本教程只推荐这两家的原因——大厂、免费、稳定，三者都占。
诚实提醒："免费"都有额度上限（流量、构建次数、文件大小等），个人教程/博客体量远远用不完。具体数字各平台会随时间调整，以官网当下的说明为准，我不写死过时的数字。第 2 章给你"够不够用"的量级感受。
选型 · 两个平台怎么挑

第 2 章：GitHub Pages 还是 Cloudflare Pages？

先给结论，再看细节
一句话结论：
・你的代码已经在 GitHub 上、只想最省事发个网页 → 选 GitHub Pages（你现在这个站就是它）。
・你想要更快的全球访问速度、更强的构建/函数能力，或需要国内相对更稳的访问 → 选 Cloudflare Pages。
两个都免费、都能绑自定义域名、都自动 HTTPS。新手从 GitHub Pages 起步最简单；进阶或追求速度用 Cloudflare。

费用免费（公开仓库）免费额度，个人用绰绰有余

免费域名用户名.github.io/仓库名/项目名.pages.dev
自定义域名支持，免费 HTTPS支持，免费 HTTPS

其它平台呢？ Vercel、Netlify 也免费好用，但你明确要"大厂、稳定优先"。GitHub Pages 和 Cloudflare Pages 在"背景实力 + 长期稳定 + 免费"三条上最稳妥，所以本教程只深讲这两个，不铺开介绍其它，避免你选择困难。
验证方法 · 用一句话给自己定方案
  1. 问自己：代码在不在 GitHub？在 → 先用 GitHub Pages 跑通（第 4 章），10 分钟见网址。
  2. 跑通后如果嫌慢或想要函数能力，再把同一个仓库接到 Cloudflare Pages（第 6 章），两个可以同时存在、指向同一份代码。
验证到了什么：两个平台不冲突，可先易后难、甚至并存。

GitHub Pages · 最简路径

第 4 章：GitHub Pages —— 网页点点点发布

不碰命令行也能发。先走通"纯网页操作"版

原理：GitHub Pages 会盯着你某个仓库的某个分支，把里面的 index.html 直接当网站发出去。流程：

创建仓库：登录 GitHub → 右上角 + → New repository → 填名字（如 my-site）→ 选 Public（公开） → Create。
上传文件：进仓库 → Add file → Upload files → 把你的 index.html（及其它文件/文件夹）拖进去 → Commit changes。
开启 Pages：仓库 → Settings（设置）→ 左侧 Pages → 在 "Build and deployment" 的 Source 选 Deploy from a branch → Branch 选 main、目录选 / (root) → Save。
等 1 分钟拿网址：刷新 Pages 页面，顶部会出现绿色的 Your site is live at https://用户名.github.io/my-site/。点它就是你的网站。
两种发布来源，二选一：
・Deploy from a branch（上面这种）：直接把分支里的文件当网站，最适合纯 HTML 的静态站（比如你这个教程合集）。
・GitHub Actions：需要"构建"的项目（用了 React/Vue/Hugo 等，得先编译成静态文件）走这条，用一个工作流自动构建后再发布。纯 HTML 用不到，别被它吓到。
关于网址形态（容易踩坑）：
・项目站：仓库随便命名 → 网址是 用户名.github.io/仓库名/（带子路径）。
・用户站：仓库必须命名成 用户名.github.io → 网址就是干净的 用户名.github.io（无子路径）。
子路径会影响资源引用，见第 9 章"样式全丢"的排错。
验证方法 · 确认真的发布成功
  1. 用手机流量（不连自家 WiFi）打开那个 github.io 网址——能打开就证明是公网可访问，不是只有你本机能看。
  2. 随便改一下 index.html 里一个字 → 重新 upload/commit → 等 1 分钟刷新网页，看到改动生效 = 自动更新链路通了。
  3. 浏览器地址栏看到 🔒 锁图标（https）= HTTPS 已自动开启。
验证到了什么：网址公网可访问 + 改动能自动上线 + 自带 HTTPS。
GitHub Pages · 进阶

第 5 章：绑自定义域名 + 免费 HTTPS

想要 www.你的名字.com 而不是 github.io，看这章

免费的 github.io 网址够用；但想更专业，可以绑自己买的域名。原理是在域名的 DNS 里加一条记录，指向 GitHub：

买域名：任意域名商（如 Cloudflare Registrar、阿里云、Namecheap）买一个，比如 example.com。
在仓库设置域名：仓库 → Settings → Pages → "Custom domain" 填 www.example.com → Save。这会在仓库里自动生成一个 CNAME 文件。
在域名商配 DNS：加一条 CNAME 记录，把 www 指向 用户名.github.io。（根域名 example.com 则加 GitHub 提供的几个 A 记录 IP。）
勾选强制 HTTPS：DNS 生效后（几分钟到几小时），回 Pages 页面勾上 Enforce HTTPS，GitHub 自动签发免费证书。
常见卡点：DNS 修改不是立刻生效（有缓存，可能等几十分钟）。Pages 页面若提示证书还在签发，耐心等，别反复删改。
验证方法 · 确认域名和证书都好了
  1. 浏览器访问 https://www.example.com，能打开你的站 + 有 🔒 = 域名和 HTTPS 都成了。
  2. 终端敲 nslookup www.example.com（或用在线 DNS 查询工具），看到解析指向 github.io = DNS 配置正确。
验证到了什么：自定义域名可访问、证书有效、DNS 解析正确。
Cloudflare Pages · 从 0 到 1

第 6 章：Cloudflare Pages —— 连 Git 自动发布

速度更快、能配函数。多花一步连账号，其余全自动

Cloudflare Pages 有两种发布方式，新手推荐连 Git 仓库（以后 push 就自动重新部署）：

方式 A · 连 Git 仓库（推荐）

登录 Cloudflare：dash.cloudflare.com 注册/登录。
新建 Pages 项目：左侧 Workers & Pages → Create → 选 Pages 标签 → Connect to Git。
授权并选仓库：授权 Cloudflare 访问你的 GitHub → 选中你的仓库（如 my-site）。
配置构建：纯 HTML 站点 → Framework preset 选 None、Build command 留空、Build output directory 填 /（或你放 index.html 的目录）→ Save and Deploy。
拿网址：几十秒构建完，给你一个 项目名.pages.dev 网址，公网可访问。

方式 B · 直接上传文件夹（不想连 Git 时）

创建项目时选 Direct Upload，把整个文件夹拖上去即可。适合快速一次性发布。

Cloudflare 的加分项 · Pages Functions：在项目里放一个 functions/ 目录写 JS，就能有轻量后端接口（serverless 函数）——纯静态搞不定的"处理表单、调 API 藏密钥"等，它能补上。这是它相对 GitHub Pages 的最大优势（第 7 章展开）。
验证方法 · 确认 Cloudflare 发布成功且会自动更新
  1. 手机流量打开 项目名.pages.dev，能访问 = 成功。
  2. （方式 A）改一行代码 git push → 回 Cloudflare 项目页看 Deployments 列表，自动出现一次新构建，完成后网页更新。
  3. 对比：同一份代码在 github.io 和 pages.dev 两个地址都能开——证明两平台并存不冲突。
验证到了什么：Cloudflare 发布成功、push 自动触发重新部署、可与 GitHub Pages 并存。
边界 · 静态到底能做到哪

第 7 章：静态托管支持什么、不支持什么

别拿静态托管去干动态的活——但很多"看起来动态"的其实能做
✅ 完全支持（放心用）
纯 HTML/CSS/JS
你这种手写页、带 canvas 动画的，完美支持。
前端框架构建产物
React/Vue/Svelte 等 build 出来的静态文件，支持（GitHub 用 Actions 构建，Cloudflare 自动构建）。
静态站生成器
Hugo、Jekyll、VitePress、Astro 等生成的博客/文档站，支持。
调用第三方公开 API
前端 JS 直接 fetch 别人的公开接口（天气、汇率等），支持。
SPA 单页应用
支持，但要配好"找不到路由回退到 index.html"（第 9 章）。
❌ 不支持（纯静态做不了）
自己的后端/数据库
没有服务器帮你跑 PHP/Java/Python、连 MySQL。要存数据得靠外部服务。
服务端渲染 SSR
每次请求在服务器现算 HTML 的模式，纯静态托管不行。
藏密钥的操作
前端代码是公开的，不能把 API 密钥写在 JS 里（谁都能看到）。
那"动态需求"怎么补？（不用自己养服务器）
・Cloudflare Pages Functions / Workers：写轻量 serverless 函数，处理表单、代理请求、藏密钥。免费额度够个人用。
・第三方 BaaS：数据库/登录用 Supabase、Firebase 这类"后端即服务"，前端直接调。
・表单类：Formspree 等专门收表单的服务。
思路：静态站负责"展示"，把"动态那一小块"外包给 serverless 或 BaaS——既省钱又不用运维服务器。
验证方法 · 判断你的需求要不要"补动态"
  1. 列出你页面上每个功能，逐条问："这需要在服务器上保存数据 / 保密 / 现算吗？"
  2. 全部"否" → 纯静态托管够了，零成本。有"是" → 那几个功能用 Cloudflare Functions 或 Supabase 补，主体仍然免费静态托管。
验证到了什么：分清哪些能纯静态、哪些要外包，避免为一个小功能去租整台服务器。
★ 本教程重点 · 让 AI 一口气发布

第 8 章：全程靠 AI 发布（完整账号 + 命令清单）

你现在就是这么发的。这一章把整条链路拆成"人做一次"+"AI 反复做"

核心分工：凡是涉及"登录授权"的一次性动作，由人在浏览器完成（AI 不碰密码）；之后所有建仓库、推代码、开 Pages 的重复动作，AI 用命令行一条龙搞定。

人类只需一次性做这三件事（之后可完全交给 AI）：
① 注册 GitHub 账号；② 装好 git 和 gh（第 3 章）；③ 跑一次 gh auth login 用浏览器授权。
完成后，令牌安全存在本机，AI 直接调用 gh 即可，全程不接触明文凭据——这也是最安全的姿势。

🅰 路线一：GitHub Pages 全自动（推荐给 AI）

把下面这段当作给 AI 的"标准作业"。假设你的网站文件在当前文件夹，含 index.html：

# 0) 前提：人已完成 gh auth login。先确认身份 & 拿到用户名
gh auth status
OWNER=$(gh api user --jq .login)   # 自动取你的 GitHub 用户名

# 1) 初始化本地 git 仓库并提交
git init
git add -A
git commit -m "init: my static site"

# 2) 一条命令：在 GitHub 建公开仓库 + 关联 + 推送
gh repo create my-site --public --source=. --remote=origin --push

# 3) 开启 GitHub Pages（从 main 分支根目录发布）
gh api -X POST repos/$OWNER/my-site/pages \
   -f "source[branch]=main" -f "source[path]=/"

# 4) 拿到最终网址
gh api repos/$OWNER/my-site/pages --jq .html_url
逐条在干嘛：
・gh repo create ... --source=. --push：一步完成"建远程仓库 + 设为 origin + 推送本地代码"。
・gh api -X POST .../pages：调 GitHub 接口打开 Pages 开关并指定发布分支/目录（等于第 4 章第 3 步的网页操作，只是命令化）。
・最后一条打印 html_url，就是 https://用户名.github.io/my-site/。
以后更新网站：只要 git add -A && git commit -m "..." && git push，Pages 自动重新发布，无需再动开关。
可能的坑（让 AI 有 fallback）：
・第 3 步若报 Pages 已存在/权限问题，AI 可改用网页操作（第 4 章第 3 步）兜底，或改 -X PUT 更新已存在的配置。
・仓库若私有，免费版 Pages 可能受限，建议用 --public 公开仓库最省心。
・首次发布后 Pages 构建需 ~1 分钟，网址可能短暂 404，等一会儿再验证。

🅱 路线二：Cloudflare Pages 全自动（用 wrangler 直传）

如果要 AI 发到 Cloudflare（更快的 CDN），用官方 wrangler 命令行"直接上传"，不必连 Git：

# 0) 人先跑一次浏览器授权（AI 不碰密钥）
npx wrangler login

# 1) 创建 Pages 项目（生产分支设为 main）
npx wrangler pages project create my-site --production-branch=main

# 2) 把当前文件夹作为静态资源直接部署
npx wrangler pages deploy . --project-name=my-site

# 部署完终端会打印 https://my-site.pages.dev 之类的网址
给 AI 的完整心法（可直接贴进 prompt）：
  1. 先 gh auth status / wrangler whoami 确认已授权；没授权就停下来提示人类去授权，不要试图代填密码。
  2. 用 gh api user --jq .login 动态获取用户名，不要硬编码。
  3. 按路线一或二执行；每一步跑完检查返回值/退出码，失败就走对应 fallback。
  4. 最后打印出最终网址并自我验证（curl -I 网址 看是否 200，见下方验证）。
  5. 永不把 token/密码写进文件或提交进 Git。
验证方法 · AI 自己确认"真的发布成功了"
  1. 命令行验证：curl -I https://用户名.github.io/my-site/，看到 HTTP/2 200（首次可能 404，等 1 分钟重试）。
  2. 内容验证：curl -s 网址 | grep "<title>"，打印出你页面的标题 = 内容正确上线。
  3. 人工复核：手机流量打开网址，肉眼确认页面和本地一致。
验证到了什么：AI 不用"我以为发好了"，而是用 HTTP 状态码 + 页面内容客观确认发布成功。

第 9 章：常见问题排错

发布后最容易撞的几个坑，对症下药
症状原因 & 解法
网址 404 打不开① 刚开启 Pages，还在构建，等 1–2 分钟；② 分支/目录选错（要选有 index.html 的那个）；③ 仓库私有且免费版受限 → 改公开。
页面打开了但样式/图片全丢多半是路径问题。项目站网址带子路径（/仓库名/），而代码里用了 /style.css 这种绝对路径会找错。改成相对路径 ./style.css，或用户站（仓库名=用户名.github.io）避免子路径。
改了代码但网页没变① 还在构建，等一下；② 浏览器缓存，强制刷新（Ctrl+F5）或无痕窗口；③ 确认真的 push 上去了（git log 看提交）。
SPA 刷新子页面 404单页应用要配"回退到 index.html"：GitHub Pages 加一个 404.html 兜底；Cloudflare 用 _redirects 文件把所有路径指向 /index.html。
HTTPS 证书没生效自定义域名的 DNS 刚改，等生效；Pages 里勾上 Enforce HTTPS 后再等证书签发。
中文文件夹名网址乱码URL 里中文会被编码成 %xx。想网址干净，子文件夹用英文名（本合集就是这么做的：stock-basics 而非中文）。
验证方法 · 排错后确认修好了
  1. 改完 → push → 无痕窗口打开网址（避开缓存）→ 逐项确认样式/图片/路由都正常。
  2. 用 curl -I 网址 复查状态码从 404 变成 200。
验证到了什么：用无痕窗口 + curl 客观确认问题真的解决，而不是被缓存骗了。

GitHub Pages 全自动（复制即用）

gh auth status
OWNER=$(gh api user --jq .login)
git init && git add -A && git commit -m "init"
gh repo create my-site --public --source=. --remote=origin --push
gh api -X POST repos/$OWNER/my-site/pages -f "source[branch]=main" -f "source[path]=/"
gh api repos/$OWNER/my-site/pages --jq .html_url
# 之后更新：git add -A && git commit -m "..." && git push

Cloudflare Pages 全自动（直传）

npx wrangler login
npx wrangler pages project create my-site --production-branch=main
npx wrangler pages deploy . --project-name=my-site

验证发布是否成功

curl -I https://用户名.github.io/my-site/      # 看 200
curl -s https://用户名.github.io/my-site/ | grep title
